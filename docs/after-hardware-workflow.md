# 实物到位后的完整工作步骤

本流程用于实物到位后逐项执行。当前已完成的是离线软件准备，真实通信、校准、运动、
示教、抓壶和水量反馈尚未验收。每一步记录实际结果，通过后再进入下一步。
当天记录放在 `data/commissioning/<session-id>/`，使用 [现场记录模板](commissioning-record.md)。

## 总顺序与通过条件

| 顺序 | 工作 | 完成标志 |
|---|---|---|
| 1 | 清点、装配、固定与接线 | 实际套件、电源、接线、支撑和断电方式确认 |
| 2 | 识别 USB-CAN，选择运行系统 | 型号/VID/PID/驱动明确，设备由一个系统持有 |
| 3 | CAN 配置与只读电机检查 | 1–7 在线；新鲜位置反馈在程序运动前验证通过 |
| 4 | 官方零位与参数校准 | 姿态、零位、参数回读和版本记录齐全 |
| 5 | 官方界面验证基础控制 | 单关节、夹爪、短动作、退出与停止行为可控 |
| 6 | 接入并验证程序控制 | 实测参数、受限执行、反馈、超时和停止策略通过 |
| 7 | 固定位置空茶壶抓放 | 抓稳、抬升、放回能够重复完成 |
| 8 | 固定相机、校准与示教设备 | 视频稳定，输入设备兼容，字段/单位/同步明确 |
| 9 | 采集、检查和备份真实数据 | 成功示教完整，失败有标签，备份校验通过 |
| 10 | ACT 训练与独立摆位评估 | 有效检查点，20次抓放至少18次成功 |
| 11 | 固定杯冷水倾倒，再随机杯定位 | 负载、壶嘴对准、杯身份与位置跟踪稳定 |
| 12 | 水量反馈、余流与最终验收 | 独立测量最终容量比例，首版85%–95%，无洒水 |

步骤1–5主要使用现有诊断和官方界面；步骤6需要后续现场开发真机适配。
目前项目控制层只接受mock，填写硬件模板不会开启动作。真实policy rollout和液位估计也待接入。

## 1. 清点并准备台架

确认B601-RS、夹爪、USB-CAN、电源/信号分离板、线材和固定夹具；相机与Leader型号一并记录。
成品套件先按实际清单检查，不重写电机ID。电源按铭牌和实际套件要求核对。
固定底座，安排机械支撑和能立即执行的断电方式；电机接插件接线时断电。
保存装配、接线和零位准备姿态的照片，检查线缆在预期动作范围内不会拉扯。

参考 [Seeed官方首次运行流程](https://wiki.seeedstudio.com/cn/rebot_b601_rs_getting_started/)。

## 2. 识别适配器并选择接入路径

先将USB-CAN接到电脑，记录Windows设备管理器中的设备名、VID/PID和驱动状态。
CAN适配器以实际型号和固件判断，不使用蓝牙COM口代替。

沿用现有WSL开发环境时，需要把适配器附加到Ubuntu；Windows原生PCAN是另一条独占路径。
在 [首次连接文档](robot-first-connection.md) 中选择匹配实际设备的路线。
WSL USB附加步骤以 [微软官方说明](https://learn.microsoft.com/en-us/windows/wsl/connect-usb) 为准：

```powershell
# 已安装usbipd-win后，在管理员PowerShell首次共享：
usbipd list
$rebotCanBusId = Read-Host '输入已核对USB-CAN的BUSID'
usbipd bind --busid $rebotCanBusId

# Ubuntu保持运行，在普通PowerShell附加：
usbipd attach --wsl --busid $rebotCanBusId
```

如果换窗口，重新设置变量。只共享已识别的适配器，不同时启动Windows和WSL控制程序。
WSL中确认 `lsusb` 能看到设备，`ip -details -br link` 出现对应CAN接口。
若没有接口，先查USB附加和实际驱动；此时不改电机ID或零位。

## 3. 配置总线并只读检查

以下Linux命令需要先确认真实接口。项目can-up入口目前接受can0/can1等can数字名称。

```bash
cd ~/projects/rebot-tea
ip -details -br link
read -r -p '输入已确认的CAN接口名：' REBOT_CAN_CHANNEL
bash scripts/control_linux.sh can-up "$REBOT_CAN_CHANNEL"
bash scripts/control_linux.sh doctor "$REBOT_CAN_CHANNEL"
bash scripts/control_linux.sh probe "$REBOT_CAN_CHANNEL"
```

can-up需要sudo，只设置已有接口为1Mbps；probe发送查询帧，不使能、不写零、不改ID。
检查 `artifacts/motors-linux.json`：1–7在线，位置数值有限且每次读取有新采样时刻。
诊断结果复制到当天记录目录，下一次运行会覆盖artifacts中的默认文件。

7号缺失或某个ID不响应时，先查接线、电源、总线与实际ID。
若Ping正常但位置读取超时，记录该状态并通过官方界面核对固件/读取条件，
本项目不会为了读位置自动使能。在线检查后可按官方流程核对校准，
新鲜位置问题解决前不开始程序化运动。

## 4. 官方校准与参数回读

确认台架支撑和操作者到位后，由操作者启动官方控制界面：

```bash
bash scripts/control_linux.sh gateway "$REBOT_CAN_CHANNEL"
```

打开 [MotorBridge Studio](https://motorbridge.github.io/motorbridge-studio/)，
连接 `ws://127.0.0.1:9002`，选择 `rebot-arm-robstride`。
扫描1–7，根据厂家规定姿态完成零位设置，再套用对应RS参数模板并回读。
写零表示把当前姿态定义为零位；先摆到规定姿态，不把写零当作自动回零。
保存校准照片、固件、电机型号、实际ID、参数导出文件及回读一致的记录。

## 5. 验证官方界面基础控制

顺序为：空夹爪、单关节小幅低速动作 → 夹爪开合 → 短动作组合。
逐轴记录公共正方向、实测可用软限位、夹爪映射、到位误差和反馈时效。
数值由现场测试决定，不从合成配置或URDF直接复制。
分别确认停止、正常退出、失能、急停和断电后的行为，记录支撑与恢复方式。
完成后停止gateway；同一总线不与后续LeRobot进程并行占用。

## 6. 补齐程序控制并现场验证

**该步骤需要后续开发，当前没有可直接运行的项目真机动作命令。**
以现场记录为依据实现MotorBridge真机后端：原始电机rad到公共关节坐标的方向/零偏映射、
逐轴新鲜反馈、经过确认的驱动模式/参数、受限轨迹、到位等待、超时与异常处理。
从当前实际反馈开始；请求停止必须对应现场验证过的策略，并记录实际停止结果。
保留现有mock入口，真实执行使用单独明确的入口，不通过修改synthetic标记来绕过限制。

先重复步骤5的单关节、夹爪和短轨迹，核对速度/加速度、反馈时效及中止行为。
笛卡尔抓取还需实际TCP、桌面/障碍物几何、IK和碰撞检查；现有数学演示不证明这些条件。
程序控制稳定后，才让学习策略进入该执行链。

## 7. 固定位置抓放空茶壶

记录实际茶壶尺寸、质量、把手/壶嘴、夹持位置和放回区域；先不加水。
用已验证的控制方式完成抓稳、短距离抬升、放回，检查滑落、遮挡和夹爪状态。
无法稳定夹持时先调整机械夹持和姿态，再录制数据，避免把不稳定操作当作学习目标。

## 8. 接入相机与示教设备

固定相机并记录分辨率、实际稳定帧率、安装位置及相机键，后续采集和部署保持一致。
本项目示例相机键为scene；实际使用其他键时，训练与部署配置必须同步。
几何定位路线需相机内参、畸变处理、RGB/深度对齐、相机到base外参及真实TCP。
端到端模仿学习路线仍需检查视频连续性和图像/状态/动作同步。

确认兼容Leader（官方Arm102路线）或其他已验证输入方式。
无Leader时先解决示教输入，不能直接运行主从采集命令。
按固定版本的 [LeRobot设备说明](https://github.com/huggingface/lerobot/blob/ae2b57f12223c8c5184fcd814eb63cd9ce7de203/docs/source/rebot_b601.mdx)
完成其校准文件与小幅跟随检查，保持相同robot.id/teleop.id。
这一步的校准可能再次设置零位，应按对应姿态执行并保存新的记录。
上游RS默认退出会失能，须按现场已验证的支撑/停止方案核对有效配置后再启动。

具体校准/遥操入口见 [训练入门](training-start.md)。

## 9. 录制真实示教、检查和备份

先录3–5条成功演示，每条包含完整空壶抓起、抬升、放回；检查后再扩展摆位和方向。
使用 `.venv-training/bin/lerobot-record`，配置实际RS从臂、Leader、相机与数据集：

- robot.motor_family=rs，实际CAN通道与已验证的逐轴控制参数。
- dataset.repo_id=local/empty-teapot-test，dataset.root为新的本地目录。
- dataset.single_task描述空茶壶抓放，初次dataset.num_episodes=5。
- dataset.fps使用实测值，dataset.push_to_hub=false；episode/reset时长覆盖完整操作。
- 标记真实来源、字段顺序、公共deg单位和校准版本；不复用合成数据目录。

固定版本的record默认在repo_id后追加日期时间。保存录制结束时的实际repo_id，
后续训练使用同一个值；若自行按session命名并设置dataset.no_stamp=true，也须保持唯一目录。
核对有效joint_limits、max_relative_target、驱动/夹爪参数和退出策略，避免直接沿用未验证的默认值。

本项目自动validate目前针对合成契约，真实数据检查需按实际schema接入，
不能把生成占位图的流程用于真实采集。
按 [数据规范](data-collection.md) 检查视频、时间、字段、单位、动作和成功/失败标签。
停止采集并finalize后执行SHA-256备份，正式数据至少有另一块存储上的已校验副本。
按整条episode、摆位和session划分训练/验证，保留失败原始记录。

## 10. 真实ACT训练与抓放验收

先按 [训练入门](training-start.md) 在实录数据上做100步检查，确认数据读取、损失、
显存、保存和重载，再增加演示覆盖与正式训练。100步不是有效策略的成功标准。
显式指定训练episode集合，留出独立摆位；正式输出与合成检查点分目录保存。

部署前检查七轴顺序、公共deg/rad转换、相机键/尺寸、处理器和动作约束。
通过步骤6的真实执行链低速评估未见摆位；当前项目尚未接通真实policy rollout。
记录20次独立尝试，至少18次成功。单次成功定义和CSV统计见 [任务验收](task-acceptance.md)。

## 11. 冷水倾倒与随机杯定位

抓放稳定后逐渐增加实际负载，先向固定杯少量倒冷水。
验证壶嘴/杯口对准、倾倒姿态、回正路径和负载；随后增加杯子随机摆位。
随机杯阶段需真实杯定位与持续身份跟踪，目标移动或丢失时按已验证策略停止。
现有COCO模型含cup但不含teapot，专用茶壶识别、抓持确认和对准仍需真实模型/观测接入。

## 12. 水量反馈与最终验收

独立标定杯容量，并用参考测量验证不透明杯的反馈传感方案。
记录估计/执行延迟、停止请求、实际停流时刻及最终余流，实测后设置提前停止策略。
先固定杯验证，再覆盖随机摆位、遮挡、目标丢失和反馈过时场景。
目标为容量90%，首版最终允许85%–95%；洒水或目标异常不计成功。
填写pour-trials.csv并使用已有统计工具；最终结果保留独立测量方法和原始记录。

每次结束保存日志、校准、有效配置和验收表；软件版本与实物配置形成同一可追溯版本。
发生通信、方向、夹持或反馈异常时回到对应步骤处理，不自动重启策略继续运动。
